# Implementation Plan — Synthetic Respondent Survey Harness

As of 2026-09-23. Implements [`SPEC.md`](SPEC.md) and the five-step wizard in [`DATA_FLOW.md`](DATA_FLOW.md): Survey Info → Personas → Questionnaire → Simulation → Report. Where they differ, `DATA_FLOW.md` wins.

The plan has five milestones. M1 (skeleton and contracts) is mostly done by the initial scaffold; each later milestone delivers whole wizard steps, backend and screen together. After M1, a Rust track and a UI track can run in parallel because they share only the generated types in `src/types/gen/`.

## Repo layout

```
/
├─ Cargo.toml                    workspace; default member is crates/core
├─ crates/core/                  survey-core: all logic, no Tauri (builds and tests on any OS)
│  ├─ src/db/                    open + migrations (docs/schema.sql), projects, batching writer
│  ├─ src/llm/                   LlmProvider trait, Gemini adapter
│  ├─ src/engine/                background jobs (M2–M4)
│  ├─ src/sampling.rs            quota apportionment (raking in M2)
│  ├─ src/model.rs               types shared with the UI (ts-rs)
│  └─ data/countries.json        Target Country list
├─ src-tauri/                    survey-app: Tauri shell, commands only
├─ src/                          React UI
│  ├─ features/<step>/           one folder per wizard step
│  ├─ components/                AppShell, Stepper, form primitives
│  ├─ lib/api.ts                 typed invoke wrappers + browser mock
│  └─ types/gen/                 generated by `cargo test -p survey-core`; never edit by hand
├─ docs/                         spec, data flow, this plan, test plan, schema.sql
├─ tools/                        offline scripts (M2, M5); never shipped
└─ .github/workflows/ci.yml
```

**Why two crates.** Tauri needs WebKitGTK to compile on Linux, which the Linux CI runners don't install. Keeping all logic in `survey-core` means it builds and tests anywhere; `survey-app` stays a thin shell that CI compiles on Windows. To compile the shell on Linux, install `libwebkit2gtk-4.1-dev`.

## M2 — Personas: Step 1 → Step 2 (about 1.5 weeks)

**Rust track**

0. `ScriptedLlm`: in-process fake provider for engine tests (test plan §3), moved from M1.
1. `tools/build-populations` (offline Python, never shipped): US census microdata → joint table of age band × gender × region × income × occupation group, under 1 MB, in `crates/core/data/populations/US.csv`.
2. `sampling`: draw skeletons with a seeded ChaCha RNG; rake to the quota marginals (iterative proportional fitting); apportion with the existing largest-remainder function. Countries without a census table sample each quota dimension independently. Tests: exact counts, same seed → same cohort, joint constraints respected.
3. `PersonaEnrichment` schema per product category (for mobile phones: device age, current brand, upgrade trigger), checked against Gemini's JSON Schema subset by a unit test.
4. `engine::cohort` job: batches of 8, diversity hint, screening with redraw from the same quota cell (failed personas kept as `screen_status = 'failed'`), validate → retry once → split batch, save per batch through the writer, stream `CohortProgress`.
5. Shared rate limiter (`governor`): requests per minute, input tokens per minute, requests per day, defaults from the Gemini tier.
6. `generate_cohort` starts the persona job (and, from M3, the draft job) and returns at once. `get_cohort_summary`, `list_respondents` (search in SQL), `get_respondent`, `regenerate_cohort` (new version), `lock_cohort`.

**UI track**

8. Step 2: progress while generating, five summary cards, respondent grid with search, profile drawer, Regenerate Cohort, Proceed to Questionnaire (locks the cohort).
9. Stepper rules from DATA_FLOW §2: a step opens only when its precondition holds.

## M3 — Questionnaire and Simulation: Steps 3 and 4 (about 2.5 weeks; the core, so review it hardest)

**Rust track**

1. `engine::survey_draft` job, started alongside the persona job: research type, category, countries and objective only (never personas). Research-type presets for length (DATA_FLOW §3, Step 3). Core questions saved `pending`; suggestions saved `suggested` and inactive. The output schema has no field for expected answers.
2. Critic on every drafted, added or regenerated question.
3. Step 3 commands: `get_survey`, `update_question` (`ai` → `ai_edited`, original kept), `reorder_questions`, `add_question`, `delete_question`, `approve_question`, `add_suggestion`, `suggest_more`, Redraft (replaces only unreviewed AI questions).
4. `start_simulation`: in one transaction, approve the survey and insert the run (the trigger refuses unapproved questions); snapshot model, temperature, prompt version, seed and survey hash; cost estimate and daily-quota check first.
5. `engine::run`: worker pool with `CancellationToken`; one `whole_survey` call per respondent; seeded option shuffle stored per answer; validation with one retry, then `invalid`; safety blocks stored as `refused`; answers and reasons through the writer.
6. Retry and backoff (`Retry-After` and Gemini `retryDelay`), adaptive concurrency (halve above 20% 429s, recover +1 per 30 s), pause the run on auth errors.
7. `RunProgress` every 250 ms at most: counts, cost (from the price table), average and p95 latency, throughput, concurrency, deltas, at most 20 console lines.
8. `pause_run`, `resume_run`, `stop_run` (Stop & Save → `stopped`, final); on launch, runs left `running` become `paused`.
9. Prompt templates `survey_draft.v1`, `critic.v1`, `answer.v1`, versioned and snapshot-tested with `insta`. Shared prefix first so Gemini's implicit cache can apply; the nightly live run checks `cached_tokens`.

**UI track**

10. Step 3: question list with drag and keyboard reorder, editor (type, prompt, options, scale), AI suggestions sidebar, Approve question, Run Survey Simulation locked until every active question is approved.
11. Step 4: stat cards, live console (keeps the last 500 lines), live charts from deltas, Pause Simulation, Stop & Save Progress.

**Exit:** a survey is drafted, reviewed and approved; a run on an unapproved survey is refused by the database; the six acceptance tests in SPEC §11 pass, including kill-and-relaunch and the forced 30% 429 test against the mock.

## M4 — Report: Step 5 (about 1.5 weeks)

1. `analysis`: SQL aggregates per question type (counts and %, Likert distribution and mean, numeric median and IQR), cross-tabs by any quota dimension, low base under 30. Golden-fixture tests.
2. Chart choice from question type (DATA_FLOW §3, Step 5). Reports work on `stopped` runs with n shown per chart.
3. Theme coding for open-ended questions (Pro), editable themes.
4. `engine::synthesis`: runs when a run completes or stops; saved in `syntheses`; every mention count and segment claim checked against theme coding and cross-tabs before display.
5. Exports: CSV (one row per respondent, UTF-8 BOM) and full JSON, through a save dialog; nothing uploaded.
6. UI: Step 5 charts, cross-tab table, AI synthesis panel with Regenerate, Offline export card, disclosure banner.

**Exit:** CSV opens correctly in Excel; charts match golden fixtures; synthesis never shows a number that fails the check.

## Parallelisation and agents

- **Sequence:** finish M1 first. After it, the Rust and UI tracks share only `src/types/gen/`, so two people or two coding-agent sessions can work on separate branches.
- **Contracts:** only the Rust track changes types; it commits the regenerated `src/types/gen/` in the same PR, and CI rejects drift.
- **UI work without Rust:** `pnpm dev` runs the screens in a browser against the mock in `src/lib/api.ts`; extend the mock as commands land.
- **Good fits for agents:** sampler, adapter details, charts, exports, Step screens against a fixed type contract.
- **Keep a human reviewing closely:** `engine::run`, the rate limiter and the writer, where concurrency bugs hide.

## Main risks

| Risk | Mitigation |
|---|---|
| Tauri shell needs WebKitGTK to build on Linux | Keep it thin; all logic in `survey-core`; dev containers install `libwebkit2gtk-4.1-dev` to compile it locally |
| Gemini schema limits or model changes break structured output | Schema-subset unit test; nightly live check on the default models; model IDs configurable |
| Daily request quota runs out mid-run | Pre-run quota check; the run pauses with the reset time |
| Installer creeps over 15 MB | CI size check on every push |
| SQLite contention under high concurrency | Single batching writer (in place), load-tested in M3 |
| Countries without census data give less realistic cohorts | Flagged in the country list; decision pending (DATA_FLOW §7) |
| Synthetic answers show too little variation | Measured by the M5 fidelity report; temperature and persona biases are the levers |
| Fidelity score mistaken for real-world accuracy | Labelled "Fidelity" everywhere; disclosure on every result and export |
| Same model family answers and judges | Pro judges Flash; hand-check 20% of judgements (test plan S12) |
